# План: управление зависимостями приложения и тем

Задача: [2026_11_07_dependency-management.md](../tasks/2026_11_07_dependency-management.md).

Статус: выполнен 2026-11-08. Фактическая реализация, результаты и границы проверки
перечислены в карточке задачи; ниже сохранён исходный план, а не отдельная очередь.
Порядок: P0 → P1 → P2 → P3 → P4 → P5; каждый этап включает документацию
и проверки своего контракта. Rust владеет состоянием и операциями,
Python/PySide6/QML — адаптером и интерфейсом.

## Что уже есть и где остаются пробелы

- `rust_core/src/deps.rs`: поиск ресурсов, определение источников, установка,
  проверка `installed()`. `installed-assets.json` хранит путь → KDE Store id/title;
  это основа для миграции, но не полный реестр владения и связей с темами.
- `stores.rs`: установка расширений редакторов; `theme.rs::install_dependencies`
  объединяет системные пакеты в одну команду терминала. Для этой ветки успешное
  завершение терминала сейчас не сопровождается проверкой каждой зависимости.
- `paths.rs::output_bounded_for`: ограничение времени дочернего процесса.
  Завершение потомков и ожидание reader-потока после выхода родителя нужно
  проверить отдельно: потомок может удерживать stdout открытым.
- `controllers/__init__.py::installDependencies`: фоновый worker, прогресс между
  элементами, лимит 300 секунд для магазина. `cancelOperation` только ставит флаг:
  текущий вызов продолжает работать. После ошибок загрузки код может перейти к apply.
- `core/cli_core.py`: `subprocess.run` с накоплением вывода до завершения.
  Политики предложения зависимостей частично фильтруются в Python.
- `automation.rs`: единые `ask/always/never` в `app-preferences.json`.
  `Main.qml::missingDialog` не содержит «Больше не спрашивать».
- Установщик выбирает системный PySide6 или собственный venv, но не регистрирует
  полный набор зависимостей приложения.

## P1. Единый постоянный реестр в Rust

1. Добавить модуль реестра, например `dependency_registry.rs`, и версионированную
   схему. Расширить существующий `installed-assets.json`; все его читатели и
   писатели перевести на один API. Миграция сохраняет исходный файл в резервной
   копии и не создаёт второй независимо обновляемый реестр.
2. Разделить ресурс и его установленные экземпляры. Ключ ресурса строить из
   провайдера, нормализованного source id и целевого приложения/вида ресурса.
   Одна установка расширения может удовлетворять несколько названий тем;
   несколько копий одного ресурса могут существовать в user/system-каталогах.
3. Хранить источник, способ установки/удаления, фактические пути/версию,
   результат и время последней проверки, происхождение (`managed`, `external`,
   `unknown`), доказательства владения, ссылки на приложение и темы.
   Состояние ресурса отделить от состояния последней операции: ошибка установки
   не должна скрывать уже существующую рабочую копию.
4. Старые записи мигрировать как сведения об источнике. Они сами по себе
   не дают права удалять весь каталог: прежний установщик мог перезаписать
   существовавшие файлы. Неизвестное владение сохранять явно.
5. Связи пересчитывать из текущих `theme.json` и описания зависимостей приложения:
   при save/import/new/clone/rename/delete, обновлении готовых тем и refresh.
   Не выполнять сетевой поиск при чтении списка. Несопоставленные зависимости
   показывать без выдуманного source id; позднее объединять после подтверждения.
6. Запись — атомарная, с сохранением прав; блокировка read-modify-write
   предотвращает потерю изменений от CLI, GUI и установщика. Во время скачивания
   не держать блокировку всего реестра; сериализовать конфликтующие операции
   над одним ресурсом. Повреждённый файл не заменять молча пустым.
7. После аварийного завершения незаконченная операция требует перепроверки
   фактических файлов; повторный запуск не создаёт дубликатов.

Результат: реестр устойчив к миграции, повторной регистрации и конкуренции;
существующие функции определения источников читают его через единый API.

## P2. Выполнение, прогресс, отмена и проверка результата

1. Вынести оркестрацию зависимостей в Rust. Один исполнитель используется
   `deps --install`, автоматической установкой при apply и магазинами редакторов.
   План операции фиксирует стабильные resource id и текущие требования темы;
   индексы старого CLI преобразуются в id при старте, а не используются как
   долговременные ссылки.
2. Ввести состояния операции: очередь → обнаружение → загрузка → установка →
   проверка → итог (`success`, `failed`, `cancelled`, `interrupted`). События
   содержат operation id, resource id, этап, доступный прогресс и понятную ошибку.
   Не показывать выдуманный процент, если размер неизвестен.
3. Разделить ограничения соединения, простоя сети и выполнения инструмента.
   Python не должен обрывать исправную операцию раньше её Rust-лимита.
   Для интерактивного пакетного менеджера показывать ожидание пользователя;
   время нажатия Enter после завершения не должно задерживать результат операции.
4. Для обычных пользовательских инструментов реализовать управляемое завершение
   дерева процессов, ограниченное ожидание потоков stdout/stderr и очистку staging.
   Отмена текущей загрузки должна завершаться за несколько секунд, а не после
   прежнего 300-секундного таймаута. Завершение GUI/CLI не оставляет скрытую установку.
5. Для системных пакетов оставить штатный менеджер в видимом терминале.
   Оркестрацию и передачу результата выполнять Rust-командой worker вместо
   наращивания shell-логики. После команды перепроверять каждый пакет и ресурс,
   включая случай нулевого exit code без установки. Не убивать привилегированный
   пакетный менеджер посреди транзакции: поддерживаемая отмена/ожидание безопасного
   завершения должны быть явно видны и ограничены возможностями провайдера.
6. Устанавливать через staging; записывать владение только после проверки
   результата. Частично выполненную операцию сохранять по каждому ресурсу,
   не помечать весь набор успешным. При сбое сохранять работоспособную прежнюю копию.
7. После неудачной установки по кнопке «Скачать и применить» показать итог
   и явный выбор: повторить либо применить без недостающего. Отмена не применяет тему.
   Политика автоматического apply и его частичные ошибки описываются тем же контрактом.

Результат: GUI получает события во время операции, отмена действует на текущий
элемент, успех означает подтверждённую доступность ресурса.

## P3. CLI, удаление и подключение установщика

Предлагаемое расширение CLI (точный JSON закрепить до подключения GUI):

```text
theme-profile deps registry [--theme=NAME|--app] [--json]
theme-profile deps refresh [--json]
theme-profile deps install ID... [--events=jsonl]
theme-profile deps remove ID... [--confirm-shared] [--events=jsonl]
theme-profile deps operation ID [--json]
theme-profile deps cancel ID
theme-profile deps register-app --python=PATH [--json]
```

1. Сохранить `deps NAME --json/--refresh/--install` как совместимый вход к тому же
   исполнителю. Разобрать неоднозначность новых подкоманд и существующих имён тем:
   не занимать допустимые имена без однозначного синтаксиса; при необходимости
   выбрать отдельную группу `dependencies` для нового API.
2. `--json` возвращает один итоговый документ, `--events=jsonl` — поток событий
   с итогом; диагностический stderr не смешивается с протоколом. Зафиксировать
   exit codes для ошибки, частичного результата и отмены.
3. Перед удалением построить план с затронутыми темами и зависимостями приложения.
   Общий ресурс требует явного подтверждения. Ресурс, используемый активной темой,
   обозначить отдельно; обязательные зависимости работающего приложения защитить
   от удаления из самого GUI, предложив штатное обслуживание через CLI/установщик.
4. Удалять только подтверждённые manager-owned файлы в разрешённых корнях;
   проверять symlink, канонический путь и изменения после установки. Чужую или
   изменённую копию не удалять рекурсивно. Расширения удалять через провайдер;
   системные пакеты — через пакетный менеджер с его проверками зависимостей.
5. После удаления перепроверять все экземпляры: удаление user-копии может открыть
   system-копию. Состояние и ссылки тем сохраняются даже для отсутствующего ресурса,
   чтобы работали переустановка и диагностика.
6. Установщик вызывает Rust-регистрацию после развёртывания CLI/GUI и готовых тем.
   Проверка PySide6 использует выбранный интерпретатор, включая venv. Повторный
   install/update обновляет факты и связи. В bash остаётся только deployment glue.

Результат: полный цикл доступен через CLI, установщик регистрирует реальные
зависимости приложения, старые команды сохраняют поведение.

## P4. Страница управления и «Больше не спрашивать»

1. Добавить отдельный Python-контроллер зависимостей и QML-страницу «Зависимости»
   в текущую навигацию. Поток CLI читать асинхронно; список, refresh, install/remove
   не блокируют UI-поток. Python не дублирует проверку установки и политику владения.
2. Страница: весь реестр / зависимости приложения / выбранной темы; фильтр
   отсутствующих и ошибок. Строка показывает название, источник, состояние,
   происхождение, связанные темы и допустимые действия. Детали содержат пути,
   последнюю проверку и причину недоступности действия.
3. Действия: установить, удалить, переустановить, обновить состояние, повторить
   неудачные, отменить. Удаление общей зависимости показывает список затронутых тем.
   Прогресс и итог по каждому элементу остаются доступными после закрытия диалога.
4. Страница и `missingDialog` используют один исполнитель и модель операций.
   После любого результата обновляются реестр и сведения о недостающих ресурсах.
5. Галочка «Больше не спрашивать» меняет существующие `automation.store/packages`,
   без отдельного флага. Подпись объясняет область: будущие установки из магазинов
   или системных пакетов. Подтверждённая установка всей группы → `always`, явное
   «Применить без них» для всей группы → `never`; закрытие/отмена ничего не сохраняют.
   При частичном выборе не выводить общую политику из отдельных галочек:
   запоминание для такой группы недоступно с объяснением, остальные группы независимы.
6. `ask` предлагает, `always` запускает разрешённые установки с отчётом,
   `never` пропускает без повторного предложения. Неоднозначные кандидаты `exact=false`
   всё равно требуют выбора источника. Решение об автоматизации выполняется Rust;
   настройки меняют те же ключи, показывая сохранённый выбор после перезапуска.

Результат: пользователь видит состояние, управляет ресурсами и сохраняет
однозначный выбор для следующих установок.

## P5. Проверка полного цикла и документация

Обязательная матрица в изолированных HOME/XDG:

| Сценарий | Что подтвердить |
|---|---|
| Установка → удаление → переустановка | Реальные файлы и доступность соответствуют реестру, дубликатов нет |
| Одна зависимость двух тем | Один ресурс, две связи, предупреждение перед удалением |
| Уже существующий ресурс | Обнаружен как внешний, право удаления не присваивается |
| Старый installed-assets.json | Источники сохранены, владение не завышено, миграция повторяема |
| Несколько user/system-копий | Правильно определяется эффективная копия после удаления |
| 404, offline, таймаут, частичный архив | Видимая ошибка, staging очищен, повторная попытка работает |
| Exit code 0 без ресурса | Проверка отвергает ложный успех, в том числе для пакетов |
| Отмена, закрытие GUI, перезапуск | Нет скрытой установки обычных ресурсов; состояние восстановлено |
| Зависший потомок с stdout | Не блокирует окончание операции и отзывчивость GUI |
| Изменённые файлы, symlink, внешний каталог | Чужие данные не удаляются |
| Конкурентные CLI/GUI и аварийный выход | Реестр цел, обновления не потеряны |
| «Больше не спрашивать» | store/packages независимы, частичный выбор/отмена корректны, настройки переживают перезапуск |
| Install/update и theme CRUD | Зависимости приложения/тем и связи обновлены |

1. Rust unit/integration: модель, миграция, конкурентные записи, провайдеры,
   прерывание, проверка результата и безопасное удаление. Для ошибок сети —
   локальный HTTP-сервер/подставные процессы с короткими тестовыми лимитами.
2. Python offscreen/qtbot: UI остаётся отзывчивым, события и отмена работают,
   busy снимается на всех исходах, политика сохраняется. CLI/installer-тесты
   подтверждают регистрацию, повторную установку и совместимость старого CLI.
3. В изолированном окружении выполнить реальный цикл для ресурсов KDE Store,
   редактора и системного пакета; моки не считать доказательством реальной установки.
   Зафиксировать версии, источники, команды, файлы и результаты в карточке.
   Недоступный провайдер отметить как непроверенный; задачу целиком не закрывать.
4. Перед завершением — проверки из `AGENTS.md`, применимые к изменённым файлам:
   release build, cargo test/clippy, Python, CLI/installer, shellcheck, QML lint,
   переводы; новый GUI проверить в Plasma. Установленные копии обновлять только
   штатным установщиком в рамках отдельного действия по развёртыванию.
5. Обновлять вместе с каждым этапом `docs/THEMES.md` (реестр/CLI/политики),
   `README.md` (пользовательский цикл), `docs/CURRENT_APP.md` (пути/границы),
   `gui/qt-app/README.md` (контроллер/страница), `CHANGELOG.md::Unreleased`,
   переводы и `docs/MCP.md`, если затронут MCP-контракт. В конце — roadmap,
   карточку задачи и `tasks/README.md` с фактическими проверками и ограничениями.

Критерий завершения: все требования карточки подтверждены, полный цикл выполнен,
нет известных бессрочных ожиданий, недоказанного владения при удалении или
расхождения между реестром и фактической установкой. Написанный план и прохождение
одних unit-тестов не означают завершённую задачу.
