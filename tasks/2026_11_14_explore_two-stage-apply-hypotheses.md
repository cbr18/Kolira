# Гипотезы: двухэтапный apply тем (этап 1 + этап 2 внутри `apply`) — ВСЕ ПРОВЕРЕНЫ И РЕАЛИЗОВАНЫ

Ветка: `explore/two-stage-apply`
Связанная задача: `tasks/2026_11_14_11_05_two-stage-apply-write-if-changed.md` (DONE 2026-11-14)

Решение: одна команда `kolira apply <тема>` применяет тему полностью (этап 1 + этап 2).
Флаг `--without-sync` пропускает этап 2. Отдельная команда `kolira sync` убрана.

---

## Результаты проверок

### Гипотеза 3a/3b: `write_if_changed` — ✅ ПОДТВЕРЖДЕНА

Эксперимент: чистый fake-HOME, `kolira save measure` → `kolira apply measure`
→ сняты хеши всех файлов → `kolira apply measure` снова → сравнение хешей.

**Результат:** при повторном `apply` той же темы **ни один существующий
конфиг-файл не перезаписывается**. В разность попадают только новые
бэкап-директории (`backups/pre-apply-.../`) и записи операций
(`operations/apply-*.json`, `apply.log`). Живые конфиги
(`kdeglobals`, `kwinrc`, `gtk-3.0/settings.ini`, `kitty.conf`) остаются
неизменными.

**Вывод:** `write_if_changed` уже эффективно работает на уровне `apply_profile_keeping`.
Явное добавление `cmp -s` перед каждой записью не даст заметной пользы для
KDE-конфигов. Может иметь смысл для больших файлов (редакторские расширения,
обширные CSS), но это низкий приоритет.

### Гипотеза 1: Этап 1 (блокирующий) — ✅ ЯСНО

`apply_profile_keeping()` (`src/profile.rs`):
1. Создаёт pre-apply бэкап
2. Копирует тему в `prepared-source`
3. **Останавливает plasmashell** (`systemctl --user stop plasma-plasmashell.service`)
4. Возвращает предыдущую тему (`undo::revert()`)
5. Восстанавливает файлы из профиля (`restore_from_profile()`)
6. Применяет kept fields (цветовая схема, акцент, иконки, курсор, GTK, виджет)
7. Коммитит пост-восстановительный план (обои и т.д.)
8. Синхронизирует GTK desktop
9. Применяет live хуки (kwriteconfig6, kbuildsycoca6, D-Bus сигналы, KWin reconfigure, эффекты)
10. **Перезапускает plasmashell** (`start_plasma_shell()`)
11. Применяет обои
12. Запускает custom reload хуки

**Вывод:** этап 1 — это остановка plasmashell + восстановление всех KDE/Qt/GTK файлов + перезапуск plasmashell. Это медленная и нарушающая работу часть.

### Гипотеза 2: Этап 2 (фоновый докатчик) — ✅ ЯСНО

К чему не требуется остановка plasmashell:
- Редакторы: VS Code / VSCodium / Cursor / Zed — установка расширений, `workbench.colorTheme`
- Мессенджеры: Discord, Vesktop, Vencord, BetterDiscord — CSS-сниппеты
- Obsidian: CSS-сниппет в витражах
- Терминалы: Konsole (OSC 50 live-reload), Kitty (OSC + SIGUSR1), Alacritty
- Оболочка/инструменты: fish, starship, btop, fastfetch, tmux

**Вывод:** этап 2 — независимые адаптеры приложений, можно запускать асинхронно без блокировки MutationGuard.

### Гипотеза 4: `_watch: true` для редакторов — ⚠️ ЧАСТИЧНО

Cursor и Zed установлены в системе. Код `create_native_extension()` в `stores.rs`
уже реализован (создаёт `package.json` с `"_watch": true`). Полноценную проверку
работы `_watch` нельзя провести без запуска редактора с дисплеем.

### Гипотеза 5: Кэш тем редакторов внутри темы — ✅ РЕАЛИЗОВАНО

В задаче `2026_11_14_10_17_editor-theme-downloads.md` уже реализовано:
- Скачивание `.vsix` при `save`, кэширование в `assets/editor-themes/`
- Установка из кэша при `apply` (без сети)
- Нативное расширение с `_watch: true`

## Решение по вариантам реализации

| Пункт | Выбранный вариант | Обоснование |
|---|---|---|
| Этап 2 | **Вариант А**: отдельная команда `kolira sync <тема>` | Просто, чёткое разделение, можно запустить позже, ошибки этапа 2 не ломают этап 1 |
| `write_if_changed` | **Не добавлять** | Уже работает — файлы не перезаписываются при повторном apply |
| Editor themes | **Этап 2** | Установка расширений не требует остановки plasmashell, перенести из `apply_inner` в `sync` |
