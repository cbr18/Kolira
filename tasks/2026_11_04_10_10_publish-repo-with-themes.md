## Что нужно для публикации «с темами»

1. **Не публиковать снимки профилей.** В репозиторий идут переносимые темы в
   формате экспорта (`themes/<name>/`: `manifest.json`, `palette.json`,
   `bundle.json`, разрешённые ассеты) — см. задачу про .zip.
2. **Лицензии ассетов.**
   - код — MIT (как сейчас);
   - сгенерированные из палитры `.colors`/kitty/Alacritty — воспроизводимы,
     в репо хранить палитру, а не результат;
   - перекраска Kvantum — производная GPL-темы: хранить **рецепт** (база + палитра),
     не файлы; если нужны файлы — отдельный каталог под GPLv3 со своим LICENSE;
   - чужие цветовые схемы/темы (Orchis, Sweet, Layan, Fluent…) — только ссылки
     по имени + где взять;
   - base16-схемы tinted-theming — MIT, уже с атрибуцией (`data/base16/README.md`);
   - **обои** — только с известной свободной лицензией (источник и лицензия в
     manifest), иначе ссылка/без обоев. Текущие обои с хеш-именами из интернета
     публиковать нельзя без проверки.
3. **Проверки перед push:** секрет-скан (gitleaks/trufflehog) по истории,
   поиск `/home/`, размеры файлов (без LFS < 1 МБ на ассет), отсутствие
   пользовательских данных в тестовых фикстурах.
4. **Встроенные темы в приложении:** список «Готовые темы» (glass, paper,
   everforest…) из `themes/`, установка = импорт пакета.
5. **README:** скриншоты тем (свои скриншоты — можно), таблица тем, лицензии,
   инструкция «как добавить тему» (PR с `themes/<name>/`).
6. **CI (GitHub Actions):** cargo test/clippy, pytest (offscreen), bash-тесты,
   shellcheck, qmllint, проверка `themes/*` валидатором (`validate_profile` для
   пакета) и лицензионных полей.
7. **Git-гигиена:** смержить/запушить `main` и фазовые ветки, тег версии
   (`VERSION`), release notes.
