# Управление зависимостями приложения и тем

**Статус:** DONE (2026-11-08). Реализовано и проверено в пределах сценариев ниже.

**План:** [Этапы реализации и проверки](../plans/2026_11_07_dependency-management.md)
— подготовлен 2026-11-07; выполнен по разрешению пользователя, результаты ниже.

## Требования

1. Предотвратить зависание при установке зависимостей. GUI остаётся отзывчивым,
   ошибки/404/недоступная сеть/ожидание пакетного менеджера не оставляют интерфейс
   навечно заблокированным. Показывать ход установки и результат, ограничивать
   внешние операции по времени, корректно завершать неудачные операции.
2. При установке приложения и для каждой темы регистрировать зависимости в
   постоянном реестре. Хранить источник, идентификатор, фактическое состояние,
   способ установки/удаления и связь с приложением и темами. Повторная установка
   не создаёт дубликатов. Уже существующие ресурсы отличать от установленных
   менеджером; успешный запуск команды сам по себе не означает успешную установку.
3. Добавить страницу «Зависимости»: просмотр всего реестра и зависимостей текущих
   тем, установка недостающих, удаление, обновление состояния после операций.
   Показывать, какие темы используют ресурс. Удаление общей зависимости требует
   предупреждения о затронутых темах; чужие файлы и системные ресурсы не удалять
   как принадлежащие менеджеру. Системные пакеты — через штатный пакетный менеджер.
4. Проверить полный цикл: установить → проверить фактические файлы/доступность и
   регистрацию → удалить → проверить удаление и состояние реестра → переустановить
   → проверить работоспособность и отсутствие дубликатов. Включить общую зависимость
   нескольких тем, уже установленный ресурс, частичный сбой и повторную попытку.
5. В диалог установки добавить галочку **«Больше не спрашивать»**. Сохранять явный
   выбор пользователя, учитывать при следующих установках и после перезапуска;
   позволить изменить его в настройках. Согласовать с существующими политиками
   `ask/always/never`, не заводить противоречащую им вторую настройку.

## Исходное состояние (проверка кода 2026-11-07, до реализации)

- `rust_core/src/deps.rs`: определение, установка зависимостей и внешние команды.
- `rust_core/src/automation.rs`: сохраняемые политики `ask/always/never` для
  магазинов и пакетов; GUI-настройки автоматизации уже существуют.
- `qml/Main.qml`, `missingDialog`: выбор зависимостей и установка перед применением;
  галочки «Больше не спрашивать» в этом диалоге нет.
- Таймауты и обработка ошибок уже добавлялись в рамках отчёта друга. Требование
  предотвращения зависаний всё равно проверить на полном цикле установки.
- Полнота существующего учёта ресурсов и удаления отдельно не аудировалась:
  перед реализацией сверить `deps.rs`, `stores.rs` и установщики, использовать
  имеющиеся механизмы вместо второго реестра с расходящимися данными.

## Архитектура и приёмка

Реестр, операции и проверки — Rust core/CLI. Python/QML — адаптер и интерфейс.
Установщик вызывает Rust для регистрации зависимостей приложения. Пути XDG-aware,
запись атомарная. Пользовательские данные при обновлении сохраняются.

- [x] Установка не подвешивает GUI; ошибки видны, повторная попытка работает.
- [x] Зависимости приложения и всех текущих тем зарегистрированы и проверены на диске в изолированной установке.
- [x] Страница показывает связи с темами и позволяет установить/удалить ресурсы.
- [x] Полный цикл установки, удаления и переустановки реально выполнен в изолированном окружении; результаты записаны ниже.
- [x] «Больше не спрашивать» сохраняется между процессами и управляется существующими настройками автоматизации.
- [x] Обновлены документация, CLI-контракт, GUI-переводы и тесты изменённых сценариев.

Расследование зависания на машине друга закрыто без логов; оно не является
блокером этой задачи и не считается доказанным исправлением всех зависаний.

## Реализация

- `dependency_registry.rs`: схема 2 того же `installed-assets.json`, миграция
  с атомарной резервной копией, блокировки, источники, связи с темами/приложением,
  экземпляры, владение, контрольные суммы и методы установки/удаления.
- `dependency_jobs.rs`: состояние операций и отмена, отдельные install-workers,
  JSONL-прогресс, контроль обычных потомков, обнаружение прерывания parent CLI.
  Пакетные транзакции заканчиваются безопасно в терминале, без лишнего Enter.
- `deps.rs` / `stores.rs` / `paths.rs`: проверка результата, атомарная подготовка
  пользовательских ресурсов, сохранение происхождения, ограниченное ожидание stdout.
  Переустановка имеет резервную копию и восстановление при ошибке/отмене.
- GUI: `DependenciesPage.qml`, Qt-контроллер и единый адаптер `cli_core.py`.
  Галочки, групповые действия, отдельные столбцы **«Название»** и **«Категория»**,
  фильтры, детали, результаты, подтверждение затронутых тем.
- Диалог установки использует тот же исполнитель. Ошибка/отмена не применяет тему;
  явное применение без недостающего передаёт `--without-dependencies`.
  Решение «больше не спрашивать» сохраняется Rust до продолжения операции;
  частичный выбор не меняет политику всей группы, кандидаты не устанавливаются молча.
- Установщик регистрирует runtime с выбранным Python; CRUD тем обновляет связи.
  Подробный контракт — [docs/DEPENDENCIES.md](../docs/DEPENDENCIES.md).

## Проверка 2026-11-08

- Release build; **125 Rust unit-тестов + 9 интеграционных CLI-тестов**.
  Проверены общий ресурс двух тем, повторная установка, миграция и повреждённый
  реестр, конкурирующий refresh, внешние/изменённые файлы и symlink, ложный exit 0,
  отмена текущего элемента, восстановление после неудачной/отменённой переустановки.
- **282 Python/Qt-теста**, включая Qt-таймер во время загрузки, поток событий,
  отмену без apply, явный повтор после ошибки, порядок сохранения политики и
  освобождение busy при отсутствии CLI.
- **256 CLI/installer-проверок, 0 ошибок**: в том числе реальная регистрация
  зависимостей приложения установщиком. Прежний Broken pipe теста automation
  устранён полным чтением вывода; offline и NO_APPLY проверяются независимо.
- Clippy `--all-targets -- -D warnings`, shellcheck scripts/harness, qmllint
  всего QML, сборка переводов (**731 завершённый перевод, 0 unfinished**) и
  `git diff --check` прошли.
- **Реальный полный цикл** через `tests/e2e/dependency-cycle.py`:
  Zed `everforest` (Everforest Dark Hard (blur)); KDE Store **2380962 / Redacted**;
  пакет **jq** через настоящий `pacman` в одноразовом Arch Linux контейнере
  `tests/e2e/Dockerfile.dependencies`. Для каждого: установить → проверить
  файлы/реестр → отказ удалить общий ресурс без подтверждения → удалить →
  переустановить → повторная установка без дубликатов → удалить.
- Страница открыта и отрисована **в текущей Plasma/Wayland**, на русском;
  отдельно offscreen при обычном и увеличенном в 1,4 раза шрифте.
  `tests/e2e/dependencies-gui.py` проверяет загрузку страницы, наличие галочек и
  исходную защиту кнопки удаления. Проверены и исправлены выравнивание столбцов
  и свободное место над таблицей. Сохраняется существующее предупреждение
  Kirigami PageRow о conflicting anchors; загрузке и отрисовке страницы оно не мешает.

## Границы результата

Реальные циклы выполнялись с отдельными HOME/XDG; системный пакет — только в
контейнере. Пользовательская тема не переключалась, установленные копии приложения
не обновлялись. Тесты регистрации не означают изменение реестра живой установленной
копии: это произойдёт после штатного обновления приложения.

VS Code/Cursor проверены контролируемым CLI-провайдером; реальная загрузка их
расширений и AUR-сборка здесь не выполнялись. Полный старый friend-in-container
с переключением всех тем не запускался и закрытая пользователем карточка не
переоткрывалась. Прерывание привилегированного менеджера посреди транзакции
намеренно не производится. При аварийном завершении parent CLI во время reinstall
копия остаётся в backups; конфликтующие файлы требуют явного восстановления.
