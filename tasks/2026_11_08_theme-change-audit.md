# Аудит последних 10 смен тем с привязкой к бэкапам

**Статус:** DONE (2026-11-09), в пределах записанной ниже проверки.

## Решение пользователя

Автоматически показывать отчёт только при ошибках. Полная информация доступна
на отдельной странице аудита; хранить последние **10** смен тем и связать записи
с соответствующими резервными копиями.

## Требования

1. Добавить страницу «Аудит» с 10 последними операциями смены темы. Учитывать
   успешные, неудачные и прерванные попытки, чтобы ошибки не исчезали из истории.
   Хранить историю между запусками; обновлять её из Rust для GUI, CLI и расписания.
2. Записывать время, исходную/целевую тему, источник запуска (GUI/CLI/расписание),
   итог, применённые изменения, пропуски, ошибки зависимостей/перезапусков и
   результат восстановления. Зафиксировать обработку повторного apply той же темы.
3. При успехе не открывать автоматически полный отчёт и не показывать успешное
   всплывающее сообщение. Текущая тема и обычный прогресс остаются видны.
   При ошибке показать краткую причину и переход к соответствующей записи аудита.
   Ожидаемый пропуск по выбору пользователя и обычная отмена не считаются ошибкой.
4. Привязать запись к операции и pre-apply бэкапу по устойчивому идентификатору,
   а не по совпадению времени/имени. Если бэкап не создан, отсутствует или
   повреждён, явно показать это и отключить недоступное восстановление.
5. Из записи дать просмотр подробностей, открытие резервной копии и явное
   восстановление с подтверждением. Восстановление использует существующий
   Rust-механизм с собственной страховочной копией и записью результата.
6. Ограничивать историю 10 записями без удаления незавершённой операции и файлов,
   необходимых выполняющемуся восстановлению. Лимит истории не считать разрешением
   удалять все старые бэкапы: политику хранения связанных копий описать отдельно
   в плане, сохраняя доступность копий для видимых записей.
7. Использовать данные [защиты применения](2026_11_08_apply-protection.md),
   существующие `ApplyReport`, `apply.log` и backup layout. Полный отчёт должен
   сохраняться и при ошибке до формирования обычного успешного ответа.

## Приёмка

- [ ] История GUI/CLI/расписания переживает перезапуск, 11-я завершённая запись вытесняет самую старую.
- [ ] Успех не открывает отчёт автоматически; ошибка ведёт к правильной записи аудита.
- [ ] Отмена/ожидаемые пропуски отличимы от ошибки, детали доступны на странице.
- [ ] Запись однозначно связана с бэкапом; отсутствующая/повреждённая копия обработана.
- [ ] Восстановление и его неудача проверены в изоляции; необходимые копии не теряются при очистке истории.
- [ ] Обновлены GUI/CLI-тесты, README, документация восстановления, переводы,
      changelog и очередь задач.

## Основа реализации

Защита применения завершена: `operations/<id>.json` связывает профиль, фазу,
время, ошибки применения/восстановления и существующий pre-apply бэкап.
[Контракт](../docs/APPLY_PROTECTION.md). В этой карточке реализованы страница
GUI, ограничение хранения 10 смен и пользовательский сценарий восстановления.

## Текущая реализация приоритетной задачи

Общий [план и контракт](../plans/2026_11_08_schedule-audit-mcp.md).
Изменения выполняются по приоритету пользователя вместе с расписанием,
историей и агентским интерфейсом. Параллельная ветка исправляет UI; точки
подключения новых страниц нужно сохранить при объединении.

Расширены durable records: источник, исходная тема, частичный/полный отчёт,
изменённые пути. Реализован лимит 10 завершённых + все pending без удаления
бэкапов. Здоровье копии проверяется по манифесту/хэшам. Восстановление
завершённой смены — новая защищённая транзакция с собственной копией.
Добавлены API/CLI/MCP и GUI-страница. Успешный apply не показывает всплывающий
отчёт; ошибки ведут к истории. [Контракт](../docs/APPLY_PROTECTION.md).

Первичные тесты подтверждают восстановление, отказ при порче копии,
связь по ID и сохранность бэкапов после вытеснения записи.
