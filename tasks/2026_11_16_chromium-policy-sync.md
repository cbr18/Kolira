# Chromium / Chrome: проверка автоматического акцента

Статус: DEFERRED / P4 — 2026-11-16. Исследование native lifecycle завершено;
автоматический policy-адаптер отложен из-за потери GTK/Qt baseline в Chromium.
Это не готовая интеграция и не установленное обновление.

## Цель и критерий решения

Акцент из палитры без ручного load/reload/reset, с возвратом исходного оформления,
включая пользовательскую тему браузера. Нельзя переписывать Preferences, UI CSS,
иконки, текст или завершать браузер. Возврат файлов сам по себе недостаточен:
браузер должен автоматически вернуться к прежнему виду.

Уточнение пользователя: интеграции, требующие ручного выбора/reload/сброса или
перезапуска после Apply, перемещаются в конец очереди с пометкой. В
[приоритетах](../docs/APP_COVERAGE_PRIORITIES.md) добавлен P4. Отдельно отмечены
«РУЧНОЕ» и «АВТО НЕ ПОДТВЕРЖДЕНО»: отсутствие проверки не называется поломкой,
но файловая поддержка больше не выдаётся за готовую live automation.

## Что проверено

Native **Chromium 157.0.8103.38**, установленный на машине бинарник, запущен
в одноразовом Docker/Xvfb с изолированным HOME. Браузер работает как UID 1000;
только тестовый writer контейнера пишет собственный policy-файл в контейнерный
`/etc/chromium/policies/managed/kolira-appearance.json`. Ни host HOME, ни host
`/etc` в контейнер не подключались; сеть отключена. Репозиторий и `/usr` read-only.

Для всех восьми комплектных палитр проверяются одновременно:

- managed `autogenerated.theme.policy.color` совпадает с реальным palette accent;
- у открытого Chromium меняются вычисленные native-цвета новой вкладки;
- после снятия политики все theme preference **values** и вычисленные цвета
  совпадают с baseline; policy больше не managed. Provenance metadata браузера
  может изменяться с default на user-controlled без изменения значения.

Обновление политики: `--refresh-platform-policy --no-startup-window` существующему
изолированному экземпляру. В policy только `BrowserThemeColor`; неподтверждённый
`BrowserColorScheme` не используется. Предпочтения читаются через диагностическую
страницу браузера. Исходные GTK/Qt/day/night выбираются штатными Appearance controls,
тема-расширение загружается только из временной копии. Preferences не редактируются.

### Результаты

| Исходное оформление | Результат |
|---|---|
| Стандартное | Восемь Apply → снятие policy → полный возврат PASS |
| Личная тема-расширение | Восемь Apply → снятие policy → возврат исходного theme id/значений/цветов PASS |
| GTK | Акцент применяется; после снятия policy `extensions.theme.system_theme` меняется **1 → 0**, baseline потерян — FAIL |
| Qt | Акцент применяется; после снятия policy `extensions.theme.system_theme` меняется **2 → 0**, baseline потерян — FAIL |
| Личный dark/light | По восемь Apply → снятие policy → возврат значений/цветов для каждого режима PASS |

Итого 32 успешных цикла для четырёх baseline; два провала возврата GTK/Qt.
GTK/Qt-дефект воспроизведён на первой палитре Paper: проверка остальных цветов
не исправила бы сам контракт возврата. Обычный файловый backup политики этого
не решает: браузер уже изменил своё внутреннее состояние. Google Chrome, прочие
версии Chromium, Flatpak/Snap, portable и несколько пользователей не проверены;
результат Chromium не переносится на них как обещание поддержки.

## Решение

Экспериментальный privileged writer, его installer/polkit action и подключение к
Plan/journal **убраны из текущей работы до поставки**. Рабочий Apply не пишет
системные policies; root-helper не ставился, живой Chromium пользователя не менялся.
В репозитории остаётся только воспроизводимый изолированный исследовательский тест.
Прямая запись browser Preferences или ручное «переключи обратно GTK» не являются
приемлемым обходом дефекта.

Chromium/Chrome остаются в P4 с существующим ручным extension-ресурсом. Это
историческая частичная поддержка, а не рекомендуемый автоматический сценарий.
Для возврата в основную очередь нужен подтверждённый безопасный native Apply →
обновление работающего браузера → возврат для **всех** baseline, включая GTK/Qt,
без ручных действий и прямой правки Preferences. Политика системная и действует
на все профили: будущий адаптер обязан также сохранять административные настройки
и не прятать чужие BrowserThemeColor policies.

## Как воспроизвести

Существующий локальный образ `ktm-friend`, системные Chromium/Python/Playwright,
Xvfb. Из корня репозитория (подстановка `$PWD` — путь только для read-only mount):

```bash
docker run --rm --network none --shm-size 512m \
  -v /usr:/usr:ro -v "$PWD:/src:ro" \
  -e KOLIRA_POLICY_NATIVE_CONTAINER=1 -e HOME=/tmp/policy-home \
  -e LIBGL_ALWAYS_SOFTWARE=1 -e GALLIUM_DRIVER=llvmpipe \
  -e __EGL_VENDOR_LIBRARY_FILENAMES=/usr/share/glvnd/egl_vendor.d/50_mesa.json \
  -e __EGL_EXTERNAL_PLATFORM_CONFIG_DIRS=/nonexistent \
  ktm-friend xvfb-run -a -e /dev/stderr \
  -s '-screen 0 1280x900x24 -nolisten tcp -ac -extension GLX' \
  python3 /src/tests/e2e/chromium-policy-native.py
```

Скрипт намеренно возвращает exit 1 при потере baseline; GTK/Qt-проверки нельзя
удалять ради зелёного результата. Для отдельных сценариев доступны
`--baselines default extension`, `--baselines gtk qt`,
`--baselines user-dark user-light`. По умолчанию проверяются все шесть baseline.
Тест не подключён как всегда зелёная проверка CI и не устанавливает интеграцию.

Локальные протоколы: `/tmp/kolira-policy-final-probe.log` (default/extension PASS,
GTK/Qt FAIL; первый способ задания личного режима через settingsPrivate оказался
недоступен), `/tmp/kolira-policy-mode-probe.log` (повтор с реальным Appearance
select: оба режима, все восемь палитр PASS). Ошибка подготовки fixture
не считается дефектом браузера.

Общие проверки текущего дерева: release build, **276 Rust**, **345 Python/Qt**,
**260 shell**, clippy `-D warnings`, shellcheck, cargo fmt и py_compile PASS.
Код/темы этой задачи в установленную копию не переносились. Пользовательские
BreezeLight/BreezeDark, wallpaper accent Glass/Material You и исключение LibreOffice
сохранены.
