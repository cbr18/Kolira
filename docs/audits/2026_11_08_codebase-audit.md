## Подтверждённые дефекты

P1 — возможна запись за границами оформления или потеря пользовательских
изменений. P2 — функциональная ошибка, утечка либо нарушение контракта.

### F01 · P1 · Пакет темы может перезаписывать посторонние файлы

- Места: `gui/qt-app/src/core/rust_core/src/share.rs:529`,
  `theme.rs:246`, `theme.rs:900`, `profile.rs:1222`, `profile.rs:1054`
  (последние четыре пути относительно того же `src/`).
- Импорт проверяет относительные пути, контрольные суммы и версию схемы,
  но не соответствие `assets.kind` разрешённой области назначения. Apply
  добавляет произвольный существующий asset в список восстановления;
  для неизвестного файла действует копирование целиком.
- Воспроизведено: ZIP с корректным `export.json`, `theme@2` и asset
  `{"kind":"custom","name":"probe","path":".ssh/config","origin":"user","redistributable":true}`
  успешно импортирован. `apply probe --without-dependencies --json` вернул
  успех и заменил исходный `.ssh/config` содержимым ZIP в изолированном HOME.
  `KTM_THEME_NO_APPLY=1` отключает внешние команды, но не файловые записи.
- Исправление: единая проверка назначения и типа ресурсов в Rust при импорте,
  загрузке и применении, включая вложенные пути, symlink и каталоги-предки.
  Проверять всю операцию до первой записи; сохранённые локальные темы также
  считать входными данными. Проверка `..` сама по себе недостаточна.
- Уверенность: 100/100. Это не ZIP traversal: путь нормальный, ошибочна область
  разрешённых файлов. Пакет не должен получать произвольную запись в HOME.

### F02 · P1 · Полный сбой применения возвращает успех и очищает staging

- Место: `gui/qt-app/src/core/theme_core.py:1303`.
- `AppThemeCore.apply()` собирает ошибки, безусловно очищает `_staged` и
  `_staged_configs`, затем возвращает `Result.ok`, даже если не записано ничего.
- Воспроизведение с подставной `_cli_field_set`, возвращающей
  `(set(), ['simulated write failure'])`: до применения одна подготовленная
  правка, после — ноль; `success=True`, сообщение `Applied 0 change(s)` с ошибкой.
- Ошибка затрагивает Inspector и MCP; следующий шаг создания профиля может
  продолжиться после несостоявшейся записи.
- Исправление: структурированный полный/частичный сбой, сохранение неудачных
  правок для повторения, остановка зависимых операций. Уверенность: 100/100.

### F03 · P2 · MCP завершается на некорректной форме JSON

- Места: `mcp/theme_profile_mcp.py:99`, `:660`.
- `handle()` предполагает объект и вызывает `.get()` до защищённого блока;
  `main()` перехватывает только синтаксическую ошибку JSON. `[]`, `null` и
  `tools/call` с `params: ["bad"]` вызывают необработанный `AttributeError`.
- Воспроизведено прямым вызовом обработчика без создания реальных core.
- Исправление: проверять envelope/params/arguments, возвращать ошибку протокола
  и продолжать обслуживать следующие запросы. Уверенность: 100/100.

### F04 · P2 · MCP проверяет имя создаваемой темы после живых изменений

- Место: `mcp/theme_profile_mcp.py:477`.
- `create_profile` сначала вызывает `set_component`/`apply`, затем `save_profile`,
  где проверяется имя. Невалидное имя не предотвращает предыдущие мутации.
- Подставной core подтвердил порядок для `name='../bad'`, приложения btop:
  `set_component('btop', 'dark')` → `save_profile('../bad')` → ошибка имени.
  Реальные приложения в воспроизведении не менялись.
- Исправление: валидировать имя и весь запрос до побочных эффектов; обеспечить
  транзакционный сценарий подготовки. Уверенность: 100/100.

### F11 · P2 · Внешняя команда обходит общий таймаут

- Место: `gui/qt-app/src/core/rust_core/src/theme.rs:929`.
- `bat cache --build` вызывается через прямой `Command.status()` без ограничения
  времени. Общий `status_bounded` и `KTM_COMMAND_TIMEOUT` здесь не используются.
  Зависший bat удержит apply после восстановления файлов и до получения отчёта.
- Подтверждено чтением ветки исполнения; зависание bat в живой сессии не запускали.
- Исправление: общий ограниченный исполнитель и явное отражение ошибки/таймаута
  в отчёте. Проверить остальные прямые `.status()`/`.output()` на применимость
  того же контракта, не заменять вызовы механически. Уверенность: 99/100.

## Архитектурные проблемы

### A01 · Единый Rust core соблюдается не полностью

FFI-ядро удалено, но Python содержит действующую бизнес-логику и мутации:

| Место | Что выполняется в Python |
|---|---|
| `core/theme_core.py:1430`, `:1470`, `:1486`, `:1527` | Разбор/изменение JSONC, TOML, INI, user.js, запись файлов, Undo/Revert. |
| `core/app_theme_adapters.py:197`, `:418`, `:515`, `:576` | Запись настроек приложений. |
| `core/theme_bundle.py:763`, `:796` | Создание ресурсов цветовой схемы и Kvantum. |
| `core/cli_core.py:644`, `:654` | Прямой вызов Plasma для обоев и сохранение настроек. |
| `core/tracked_apps.py`, Rust `tracked_apps.rs` | Отдельные описания приложений и определения путей. |

Пути Python относительно `gui/qt-app/src/`. Эти ветки вызываются GUI/MCP;
их нельзя удалить как неиспользуемые. Нужно переносить операции в Rust,
оставляя Python отображение данных и Qt-сигналы, а затем удалять дубли.
Утверждение roadmap «парсинг конфигов и мутации выполняются в Rust» требует
оговорки до завершения переноса. Иначе будущие MCP, rollback и аудит будут
видеть разные наборы операций в зависимости от интерфейса.

### A02 · Проверки GUI не являются обязательным барьером CI

`.github/workflows/ci.yml:37` задаёт Python job `continue-on-error: true`;
security job также информационный. Shell/installer и QML-проверок в workflow нет.
Зелёный CI не означает успешную проверку приложения целиком. Предложение:
стабилизировать обязательный offscreen-набор, добавить обязательные проверки
изменяемых контрактов; нестабильные live-сценарии оставить отдельно.

Общая сериализация/восстановление после частичного apply уже имеют
[открытую карточку](../../tasks/2026_11_08_apply-protection.md); этот аудит
не утверждает, что существующая блокировка зависимостей защищает всю смену темы.
