# ТЗ: редизайн конструктора тем

> **Статус:** реализован первый программный контур v2 (`ThemeBundleCore`, адаптеры приложений, QML-страницы, MCP).
> **Цель документа:** определить новый продуктовый смысл Theme Inspector, структуру информации и минимальные возможности.
> **Связано:** `docs/TZ-THEME-INSPECTOR.md` — старая спецификация инспектора конфигов; новый документ её замещает по продуктовой модели.

---

## 1. Проблема текущего подхода

Сейчас Theme Inspector строится вокруг просмотра отдельных параметров и конфигурационных файлов. Из-за этого:

- сложно понять, какая именно тема KDE/Plasma сейчас используется;
- Plasma, обои, Kvantum, GTK и темы приложений лежат на одном уровне без нормальной иерархии;
- пользователь должен вручную знать и вводить названия тем приложений;
- выбор Kvantum и GTK выглядит как второстепенные поля, хотя это отдельные подсистемы оформления;
- профиль хранит в основном снимки файлов, а не понятный комплект тем;
- валидация, сырые конфиги и технические параметры занимают место, предназначенное для главного сценария.

Нужен не «инспектор конфигов», а **конструктор темы рабочей среды**.

---

## 2. Что должен делать продукт

Приложение должно позволить пользователю:

1. Посмотреть, какие конкретные темы KDE/Plasma, Qt, GTK и приложений сейчас активны.
2. Выбрать установленные темы из списков, а не вводить названия вручную.
3. Настроить выбранные темы и получить пользовательские производные темы там, где это возможно.
4. Сохранить весь комплект как профиль/тему.
5. Применить профиль и получить единообразную среду оформления.
6. Для каждого приложения видеть его блок настроек и выбор темы.

### Не цель

- Не дублировать все возможности KDE System Settings.
- Не показывать пользователю сырые ключи конфигов как основной интерфейс.
- Не требовать ручного редактирования файлов.
- Не обещать универсальное управление темами любых приложений без адаптера.
- Не перезаписывать установленные системные темы KDE, Kvantum или GTK.

## 3. Термины

| Термин | Значение |
|---|---|
| **Активная тема** | Состояние, которое сейчас реально использует система. |
| **Профиль** | Сохранённый комплект компонентов темы и их значений. |
| **Выбранный профиль** | Профиль, который пользователь просматривает. По умолчанию read-only. |
| **Черновик** | Изменённый профиль или активная тема, ещё не сохранённые и не применённые. |
| **Базовая тема** | Существующая установленная тема, взятая за основу. |
| **Производная тема** | Пользовательская тема, созданная путём копирования и изменения базовой. |
| **Компонент** | Типовая часть темы: Plasma Style, цвета, Kvantum, GTK, обои и т. п. |
| **Адаптер приложения** | Модуль, который умеет обнаруживать темы конкретного приложения и применять их. |

На экране всегда должен быть явный статус: **Активная тема**, **Выбранный профиль** или **Черновик**.

## 4. Продуктовая модель

### 4.1. Тема — комплект, а не набор ключей

Один профиль описывает:

```text
ThemeBundle
├── KDE / Plasma
│   ├── Global theme
│   ├── Plasma Style
│   ├── Color scheme
│   ├── Window decoration
│   ├── Icon theme
│   ├── Cursor theme
│   └── Fonts
├── Desktop & Windows
│   ├── Wallpaper
│   ├── Corner radius
│   ├── Blur
│   ├── Translucency
│   └── Window effects
├── Qt / Kvantum
│   ├── Kvantum theme
│   └── Overrides
├── GTK
│   ├── GTK 2
│   ├── GTK 3
│   └── GTK 4
└── Applications
    ├── App A → current theme + selected theme
    ├── App B → current theme + selected theme
    └── App C → unsupported / fallback
```

### 4.2. Профиль ссылается на конкретные темы

Профиль должен хранить:

- имя и описание;
- активный/выбранный статус;
- ссылки на выбранные темы;
- настройки рабочего стола и окон;
- изменения, из которых создаются производные темы;
- имена созданных производных ресурсов;
- метаданные версии схемы и генератора.

Профиль не должен применяться через десятки разрозненных правок файлов, если для компонента существует штатная тема или команда KDE.

### 4.3. Производные темы

Если пользователь меняет базовую тему, приложение создаёт отдельный пользовательский ресурс:

- базовая цветовая схема `Breeze1` → пользовательская `MyTheme`;
- базовая тема Kvantum `OrchisDark` → пользовательская `MyTheme`;
- остальные компоненты могут ссылаться на уже установленные темы.

Правила:

- системная базовая тема не изменяется;
- производная тема создаётся только после явного изменения;
- имя производной темы уникально и принадлежит нашему приложению;
- профиль применяет именно производную тему;
- удаление профиля предлагает также удалить неиспользуемые производные ресурсы;
- нельзя удалить ресурс, на который ссылается другой профиль.

### 4.4. Миграция существующих профилей

Старые профили v1 не ломаются. При открытии их нужно по возможности преобразовать в новую модель:

- известные компоненты распознаются как ссылки на темы;
- нераспознанные значения сохраняются как legacy-настройки;
- сырой снимок файлов остаётся в Advanced и может использоваться как fallback.

```text
Theme

│   ├── Global theme & Plasma Style

│   ├── Icons & cursors
│   └── Fonts
├── Desktop & Windows
│   ├── Wallpaper
│   ├── Corners
│   ├── Blur & translucency
│   └── Effects
├── Qt & Kvantum
├── GTK
├── Applications
│   ├── App cards / pages
│   └── Unsupported apps

    ├── Diagnostics

    └── Session history / undo
```

**Validation, diff и сырые конфиги не должны определять структуру продукта.** Это вспомогательные функции Advanced.

## 6. Обзор темы

Обзор показывает **состав комплекта**, а не список параметров.

Обязательные элементы:

- название активной темы или профиля;
- явный статус: Active / Selected profile / Draft;
- краткое описание комплекта;
- основные выбранные темы;
- обои;
- количество настроенных приложений;
- кнопки:
  - **Применить** — только для черновика/профиля, готового к применению;
  - **Сохранить**;
  - **Настроить компоненты**;
  - **Открыть в System Settings** как вторичное действие.

Пример блока:

```text
Активная тема

Plasma     Breeze Dark
Colors     Breeze1
Kvantum    OrchisDark
GTK        Breeze
Icons      YAMIS
Apps       12 настроено · 3 требуют внимания

[Настроить компоненты] [Сохранить как профиль]
```

## 7. KDE & Plasma

Раздел управляет конкретными темами и ресурсами KDE.

### Компоненты

| Компонент | Основное действие | Предпросмотр | Внешний переход |
|---|---|---:|---:|
| Global theme | Выбор установленной темы | Да | System Settings |
| Plasma Style | Выбор установленного стиля | Да | System Settings |
| Color scheme | Выбор / настройка / производная тема | Да | System Settings |
| Window decoration | Выбор установленной темы | Да | System Settings |
| Icons | Выбор установленной темы | Да | System Settings |
| Cursors | Выбор установленной темы | Да | System Settings |
| Fonts | Семейство, размер, настройки | Ограниченно | Fonts KCM |

### Элемент компонента

Каждый компонент должен показывать:

- название компонента;
- текущее значение;
- короткий предпросмотр;
- выбор из установленных вариантов;
- состояние «настроен» / «по умолчанию»;
- действие **Настроить**;
- действие **Сбросить**;
- переход в KDE System Settings, если полноценное редактирование там удобнее.

Список значений всегда строится из установленных ресурсов. Нельзя требовать ввод названия вручную.

## 8. Desktop & Windows

Отдельный раздел параметров рабочей среды:

- обои;
- выбор изображения и папки обоев;
- скругление углов;
- blur;
- прозрачность;
- анимации;
- эффекты окон;
- прочие настройки KWin.

Обои и оконные эффекты — это параметры темы, но не «темы» в смысле устанавливаемых ресурсов. В интерфейсе это должно быть честно отделено от Plasma Style.

Для blur, углов и прозрачности нужен интерактивный предпросмотр или хотя бы понятная схема «до/после».

---

## 9. Qt & Kvantum

Это отдельный раздел, а не подраздел общих настроек.

Состав:

- включён/выключен Kvantum;
- текущая тема Kvantum;
- список установленных Kvantum-тем;
- выбор базовой темы;
- настройка параметров выбранной темы;
- создание производной темы;
- предпросмотр Qt-виджетов;
- переход в Kvantum Manager.

### Предпросмотр

Минимальный набор элементов предпросмотра:

- кнопка;
- line edit;
- checkbox;
- radio button;
- combo box;
- tab bar;
- list;
- scrollbar;
- disabled state;
- hover/focus по возможности.

Без предпросмотра Kvantum выглядит абстрактным списком конфигов и будет неудобен.

---

## 10. GTK

Отдельный раздел с явным разделением версий:

- GTK 2;
- GTK 3;
- GTK 4.

Для каждой версии:

- текущая тема;
- установленные темы;
- выбор темы;
- предпросмотр, если возможен;
- пометки совместимости;
- переход к системным средствам настройки.

Приложения на GTK 4/libadwaita могут игнорировать часть настроек. Это нужно отображать явно:

- «Применяется»;
- «Применяется частично»;
- «Приложение управляет оформлением самостоятельно».

Начальный вариант — выбирать существующие GTK-темы. Генерация собственных GTK-тем не требуется.

## 11. Приложения

### 11.1. Правильный UX

Каждое приложение представлено отдельной карточкой или страницей:

```text
Zed
Тема: Transparent New Darcula Darker
[Выбрать тему] [Предпросмотр] [Запустить] [Настройки приложения]
```

После выбора темы:

```text
Zed
Тема: My Theme
Состояние: выбрано, применится после Apply
```

### 11.2. Требования к приложению

Для каждого адаптера должны быть доступны:

- текущая тема;
- список установленных тем;
- применение выбранной темы;
- предпросмотр или хотя бы нативная страница предпросмотра;
- запуск приложения;
- открытие встроенных настроек темы;
- понятный fallback, если автоматическое перечисление невозможно.

### 11.3. Примеры источников тем

| Приложение | Что можно показывать | Ограничение |
|---|---|---|
| Zed | Установленные темы и режим | Нужен отдельный адаптер |
| VS Code | Темы из установленных расширений | Тема может быть не установлена |
| Cursor | Темы из установленных расширений | Аналогично VS Code |
| Obsidian | Темы текущего vault | Нужно знать выбранный vault |
| Kitty | Цветовые схемы | Нужен разбор форматов тем |
| Alacritty | Цветовые схемы | Нужен отдельный формат |

### 11.4. Fallback

Если адаптер не умеет перечислять темы:

- показывать текущее значение, если его можно безопасно прочитать;
- предлагать **Открыть настройки темы приложения**;
- не показывать TextField, требующий вводить название темы вручную, как основной способ.

## 12. Контракт адаптера приложения

Каждый адаптер должен реализовывать единый контракт:

```text
detect()           → приложение установлено?
currentTheme()     → текущая тема
installedThemes()  → список доступных тем
preview(themeId)   → предпросмотр, если возможен
applyTheme(id)     → применить тему
openThemeSettings()→ открыть нативный интерфейс
launch()           → запустить приложение
capabilities()     → какие функции поддерживаются
```

Результат каждой функции должен иметь понятный статус:

- supported;
- partial;
- unsupported;
- app not installed;
- theme not installed;
- permission denied;
- external action required.

UI строится по `capabilities()`, а не предполагает, что все приложения одинаковые.

## 13. Модель изменений

### 13.1. Черновик

Пользователь не должен бояться, что любое изменение сразу ломает систему.

Модель:

1. Изменение создаёт/обновляет черновик.
2. В интерфейсе появляется понятная панель:
   - N изменений;
   - Применить;
   - Сохранить;
   - Отменить.
3. После Apply черновик становится активной темой.
4. После Save создаётся профиль.

### 13.2. Undo / Revert

Это вторичные, но нужные механики:

- Undo отменяет последнее действие;
- Revert возвращает черновик к исходному состоянию;
- после Apply можно откатить применённые изменения;
- действие подтверждается, если оно необратимо или затрагивает много компонентов.

Undo не должен быть центральной частью продукта.

## 14. Состояния

Для всех экранов нужны:

- default;
- hover;
- focus;
- disabled;
- read-only;
- draft;
- active;
- applying;
- success;
- warning;
- error;
- not installed;
- partially supported;
- external action required.

Важные сценарии:

- приложение удалено после настройки профиля;
- производная тема удалена вручную;
- GTK-тема не поддерживает GTK 4;
- приложение имеет несколько vault/profile;
- тема приложения недоступна без установки расширения.

## 15. Поиск

Поиск должен искать:

- названия компонентов;
- названия тем;
- названия приложений;
- настройки рабочего стола.

Результаты группируются:

```text
KDE & Plasma
  Color scheme → Breeze1

Applications
  Zed → Theme
```

Поиск не должен превращать главный экран в таблицу технических ключей.

## 16. Визуальные принципы

Направление:

- нативный KDE;
- инструмент, а не демонстрация glass-эффектов;
- ясная иерархия «компонент → тема → действие»;
- достаточно контраста;
- без перегруженных карточек.

Основные принципы:

1. Сначала выбор темы, потом настройка.
2. Каждый компонент показывает значение и предпросмотр.
3. Primary action на экране один.
4. Advanced не конкурирует с основными разделами.
5. Read-only, Draft и Active визуально различимы.
6. Не полагаться только на цвет: добавлять текст, иконку или форму.

## 17. Дизайн-система и адаптивность

### Целевая платформа

- Linux, KDE Plasma 6;
- PySide6 / Qt 6;
- QML + Kirigami;
- мышь и полная клавиатурная навигация.

### Размеры

Обязательные макеты:

- 640×480 — минимум;
- 820×680 — компактное окно;
- 1280×800 — широкое окно.

На 640 px:

- нет горизонтального скролла;
- нет обрезанного текста;
- одна колонка;
- второстепенные превью можно скрывать;
- длинные русские строки переносятся;
- панель действий остаётся доступной.

### Доступность

- все действия доступны с клавиатуры;
- видимый focus;
- Tooltips доступны по hover и focus;
- Accessible.name у интерактивных элементов;
- русский текст может быть длиннее английского на 30–40%;
- учитывать увеличение системного шрифта.

## 18. Технические ограничения

- UI не должен читать и писать конфиги напрямую.
- Все данные проходят через ядро и адаптеры.
- Применение внешних команд должно поддерживать `KTM_THEME_NO_APPLY=1` для тестов и dry-run.
- Системные установленные темы не изменяются.
- Производные темы создаются только в пользовательских каталогах.
- GTK 4 и libadwaita имеют ограниченную управляемость извне.
- Если нет безопасного способа перечислить темы приложения, показывается fallback, а не фиктивный список.
- Дизайн должен использовать стандартные QQC2/Kirigami-компоненты без самописных контролов там, где можно обойтись стандартными.

## 19. Этапы реализации

### Этап 1 — каркас v2

- Новая модель ThemeBundle и профиля.
- Реестр компонентов.
- Явные состояния Active / Selected / Draft.
- Обзор комплекта.
- Выбор установленных тем без ручного ввода.

### Этап 2 — KDE/Plasma и Desktop

- Plasma Style, цвета, иконки, курсоры, шрифты.
- Обои, углы, blur, эффекты.
- Производные цветовые схемы.

### Этап 3 — Kvantum и GTK

- Выбор установленных Kvantum/GTK-тем.
- Предпросмотр Kvantum.
- Совместимость GTK 2/3/4.

### Этап 4 — приложения

- Единый адаптерный интерфейс.
- Первые адаптеры: Zed, VS Code/Cursor, Obsidian, Kitty, Alacritty.
- Fallback через нативные настройки.

### Этап 5 — качество

- Миграция профилей v1.
- Диагностика и отсутствующие ресурсы.
- Undo/Revert.
- Полная адаптивность и accessibility.

## 21. Критерии приёмки

Дизайн считается готовым, если:

1. Пользователь видит состав активной темы, а не список параметров.
2. Plasma, Desktop, Kvantum, GTK и Applications имеют понятную иерархию.
3. Все основные темы выбираются из списков установленных ресурсов.
4. Для приложений предусмотрен отдельный блок и адаптерный fallback.
5. Производные темы создаются без изменения системных базовых тем.
6. Active / Selected profile / Draft различимы на каждом экране.
7. На 640 px нет переполнения и обрезанного текста.
8. Primary action на экране один.
9. Интерфейс выглядит нативно для KDE.
10. Макет можно реализовать на PySide6 + QML + Kirigami без сложных самописных контролов.

**«Какие ключи сейчас записаны в конфигах?»**

**«Какие темы составляют мою рабочую среду, как их выбрать, настроить и сохранить как единый профиль?»**
