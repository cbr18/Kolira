# Управление зависимостями

В меню приложения откройте **«Зависимости»**. Таблица разделяет **название**,
**категорию**, состояние, источник и использующие ресурс темы. Слева — галочки
выбора; галочка в заголовке выбирает видимые строки. Фильтры показывают весь
реестр, зависимости приложения или выбранной темы, только отсутствующие и поиск.
Скрытые фильтром строки не участвуют в групповой операции.

Результаты массовых операций выводятся в отдельной прокручиваемой панели
высотой до 120 px. Длинный журнал не вытесняет таблицу ресурсов со страницы.

Кнопки: **«Установить выбранные»**, **«Удалить выбранные»**, **«Переустановить»**,
**«Проверить состояние»**, **«Остановить»**. Доступность действия проверяет Rust.
Перед удалением/переустановкой показываются ресурсы и затронутые темы, включая
активную, если она использует выбранный ресурс. Связи с темами сохраняются после
удаления ресурса, чтобы его можно было установить снова.

В «Подробнее» видны пути, происхождение, причина защиты от удаления и последняя
ошибка. Отсутствующий внешний ресурс становится доступным для установки, когда
известен поддерживаемый источник; неизвестный источник требует ручного выбора.

## Установка и применение темы

Диалог недостающих ресурсов позволяет выбрать загрузки и затем применить тему.
Точные источники выбраны изначально; результаты поиска `exact=false` требуют
явного выбора. Во время установки показывается этап и результат каждого ресурса.
Интерфейс работает во время загрузки, ошибка одного элемента не скрывает остальные.
Успех означает проверенную доступность ресурса, а не только exit code 0 команды.

При ошибке загрузки тема автоматически не применяется: можно повторить операцию
на странице зависимостей либо явно применить без недостающего. Этот выбор
использует `apply --without-dependencies` и не начинает повторные загрузки.
После отмены установки тема не применяется.

«Больше не спрашивать» запоминается отдельно для магазинов и системных пакетов
в существующих `automation.store` / `automation.packages`:

- установить всю группу и запомнить → `always`;
- применить без группы и запомнить → `never`;
- закрыть/отменить диалог или оставить галочку снятой → политика не меняется.

Частичная выборка не превращается в разрешение устанавливать всю группу.
Настройки → Автоматизация позволяют вернуть `ask` или изменить решение.
Кандидаты `exact=false` не устанавливаются автоматически даже при `always`.

## Реестр и владение

Один файл: `$XDG_CONFIG_HOME/kde-theme-profile/installed-assets.json`, схема 2.
Он содержит `sources` (происхождение ранее установленных путей), `resources`
(требования, ссылки на темы/приложение, экземпляры, состояние и методы установки/
удаления), выбранный Python для проверки runtime. Реестр не входит в экспорт темы.
Он обновляется после операций с темами и при проверке состояния. Сетевой поиск
для построения списка не выполняется.

Старый формат «путь → KDE Store id/title» сохраняется в
`installed-assets.json.pre-v2`, затем читается через тот же Rust API. Эти записи
не доказывают владение и сами по себе не разрешают удаление. Повреждённый JSON
вызывает видимую ошибку; исходный файл не заменяется пустым реестром.
Запись атомарная, сохраняет права файла; конкурирующие обновления защищены
блокировкой с ограниченным ожиданием.

Идентификатор ресурса зависит от провайдера, source id и целевого вида/редактора.
Разные названия тем одного расширения объединяются в один ресурс с несколькими
требованиями. VS Code и Cursor имеют отдельные установки. Экземпляры учитываются
отдельно: после удаления user-копии может остаться установленная system-копия.

Менеджер удаляет только ресурсы, созданные его установкой и сохранившие контрольную
сумму. Существовавшие ранее ресурсы считаются внешними. Контрольная сумма включает
содержимое, имена, права и цели внутренних символьных ссылок без перехода по ним.
Подмена самого ресурса или его корня ссылкой блокирует удаление. Изменённые файлы
также защищены. Расширения VS Code/Cursor удаляются штатной командой редактора;
файлы Zed, скопированные менеджером, — по подтверждённому списку владения.

Для системного пакета право удаления возникает только после проверенной установки
пакета, которого ранее не было. Удаление выполняется штатным пакетным менеджером
без автоматического рекурсивного удаления зависимостей. Внешний пакет не становится
собственностью менеджера после проверки или повторной установки.

Python, PySide6 и обнаруживаемые инструменты приложения регистрируются установщиком
с фактически выбранным интерпретатором (системным или venv). Их удаление со страницы
защищено; обслуживание runtime выполняется установщиком/системным пакетным менеджером.
Ресурсы внутри пакета темы обслуживаются применением самой темы; реестр зависимостей
учитывает внешние требования из `theme.json`, а не все файлы рабочего стола.

## Операции, отмена и восстановление

Операции записываются в `dependency-operations/<id>/state.json`, отмена — в токен
той же операции. После завершения процесса незавершённая запись при следующей
проверке становится `interrupted`; повторная установка перепроверяет реальные файлы.
Загрузка идёт в отдельном процессе и каталоге staging; отмена останавливает текущий
элемент и его обычных потомков. Завершение GUI/CLI также останавливает download worker.

Сеть имеет ограничения соединения и простоя, внешние инструменты — собственные
таймауты. Наследованный открытый stdout не заставляет ожидать потомка бесконечно.
Для пользовательского install-worker есть общий предел 30 минут.

Системные пакеты устанавливаются в видимом терминале, где пользователь вводит
пароль. Rust worker передаёт итог до выхода терминала; дополнительного ожидания
Enter нет. Отмена не убивает привилегированную транзакцию посреди записи: интерфейс
ожидает её безопасного завершения и пропускает следующие элементы. После часового
ожидания сообщает проверить оставшийся терминал и обновить состояние. Автоматизация
пакетов поддерживает существующие Arch Linux `pacman`/`yay`/`paru`; прочие системы
требуют ручной установки, без попытки угадать команды.

Перед переустановкой user-ресурса создаётся копия в
`backups/dependency-reinstall-*/` с `resource.json`. Обычная ошибка установки
восстанавливает прежние файлы. При отмене parent CLI пытается восстановить копию;
если обнаружены изменённые/конфликтующие файлы, сохраняет резервную копию и
показывает её путь. После аварийной потери parent CLI копия также остаётся для
явного восстановления; проверка состояния не перезаписывает конфликтующие файлы.
Успешная переустановка удаляет свою временную резервную копию.

## CLI

```text
theme-profile dependencies list [--theme=NAME|--app] [--json]
theme-profile dependencies refresh [--json]
theme-profile dependencies register-app --python=PATH [--json]
theme-profile dependencies install ID... [--events=jsonl]
theme-profile dependencies remove ID... --confirm-shared [--events=jsonl]
theme-profile dependencies reinstall ID... --confirm-shared [--events=jsonl]
theme-profile dependencies cancel OPERATION_ID
theme-profile dependencies operation OPERATION_ID
theme-profile dependencies remember --theme=NAME --policy=always|never \
  --group=store|packages [--group=...] [--selected=RESOURCE_ID ...]
theme-profile deps NAME --pending --json
theme-profile apply NAME --without-dependencies [--json]
```

Старая группа `deps NAME --json/--refresh/--install=...` сохраняется, имена тем
`list`, `refresh` и т. п. не заняты новыми подкомандами. `deps --json` дополнительно
возвращает стабильный `resource_id`; индексы остаются только совместимым входом.

Чтение списка/состояния выводит один JSON-документ. Новые install/remove/reinstall
выводят JSONL-события `started`, `progress`, `item`, `finished`; stderr содержит
диагностику. `started` даёт operation id, `finished` — общий итог и результаты
элементов. Коды выхода: 0 — успех, 1 — ошибка запуска/контракта, 2 — частичный
сбой либо отмена. У `cancel` успешная запись запроса возвращает 0; это не обещание
немедленно прервать уже выполняющуюся пакетную транзакцию.

## Проверка

Rust unit/integration и `gui/qt-app/tests/test_dependencies.py` проверяют миграцию,
общий ресурс двух тем, повторные операции, ошибочный успех провайдера, защиту
внешних/изменённых файлов и ссылок, отмену и отзывчивость Qt, сохранение политики
до применения, восстановление прежних файлов после неудачной переустановки.

Реальные провайдеры проверяются отдельно от моков:

```bash
python3 tests/e2e/dependency-cycle.py gui/qt-app/src/core/rust_core/target/release/theme-profile zed
# kde STORE_ID SCHEME_NAME — цветовая схема из KDE Store в изолированном HOME
python3 tests/e2e/dependency-cycle.py gui/qt-app/src/core/rust_core/target/release/theme-profile kde 2380962 Redacted
docker build -f tests/e2e/Dockerfile.dependencies -t ktm-dependencies tests/e2e
docker run --rm -v "$PWD:/src:ro" ktm-dependencies
```

Пакетный тест выполняет реальный цикл `jq` через `pacman` внутри одноразового
контейнера; адаптер терминала только передаёт ввод и сохраняет журнал. Реальные
ресурсы/идентификаторы магазинов могут изменяться; при недоступном источнике это
не считается успешным полным циклом. Фактические результаты — в карточке задачи.

### Асинхронные MCP jobs

`list_dependency_registry` возвращает стабильные resource IDs;
`start_dependency_operation` вызывает Rust `dependency.start` и сразу после
создания job возвращает его ID. `dependency_status` читает durable-состояние,
последний прогресс и проверенные результаты; `cancel_dependency_operation`
запрашивает штатную отмену. Привилегированная транзакция завершается безопасно.
События сохраняются в `dependency-operations/<id>/events.jsonl`, диагностика —
в `stderr.log`. Старый `install_dependencies` остаётся синхронным совместимым
интерфейсом; для управляемой долгой операции используйте новый lifecycle.

## Полосы прокрутки и язык GUI

У заголовков и строк общие ширины колонок и согласованная горизонтальная
прокрутка. Вертикальная полоса вынесена к видимому краю viewport и не уезжает
вместе с таблицей; у строк есть внутренние поля. Фильтры и действия переносятся.
Журнал имеет ограниченную высоту и отдельную прокрутку. Известные этапы и
сообщения ядра переводятся, имена/пути и неизвестный внешний вывод сохраняются.
Ошибки доступны на активном экране, диалоги используют общие поля и каналы полос.
