# Защита применения темы

Rust сериализует операции оформления через `$XDG_CONFIG_HOME/kolira/appearance.lock`.
Блокировка принадлежит процессу и освобождается при его завершении. Второй Apply
получает ошибку «Another appearance operation is running», не меняя файлы.
Один контракт используют CLI, GUI/MCP через CLI и будущий запуск по расписанию.
Запись полей, Inspector Apply/Undo/Revert, темы приложений и применение палитры/обоев
также соблюдают эту блокировку. Внутренние вложенные вызовы повторно её не захватывают;
другие потоки самостоятельны. Сохранение снимка блокируется на время Apply.
Незавершённая запись в истории не удерживает блокировку: после завершения или
гибели процесса можно выполнять следующие операции без обязательного отката.

## Фазы и результаты

Каждому профильному Apply назначается `apply-<random>`. Приватная запись
`operations/<id>.json` в каталоге данных связывает профиль, время, результат,
ошибку применения, ошибки восстановления и путь к бэкапу. Фазы:

`preparing → applying → succeeded`, либо
`preparing → failed_preparation`, либо
`applying → recovering → rolled_back | recovery_failed`.

До изменения оформления Rust проверяет пути ресурсов и чистые преобразования
конфигов, включая TOML/JSONC. Затем копирует исходную тему в
`backups/pre-apply-…/prepared-source/` и повторяет проверку уже по этой копии.
Восстановление и основные live-хуки используют её, поэтому последующее изменение
каталога исходной темы не меняет восстанавливаемые файлы.

Перед остановкой plasmashell и откатом предыдущей темы создаются обычный
pre-apply бэкап и `transaction/manifest.json` с оригиналами в `transaction/files/`.
Бэкап имеет права 0700, служебные JSON и оригиналы — 0600. Manifest хранит исходные
права, типы, ссылки и SHA-256; при восстановлении проверяется целостность копий.
Блокировка охватывает всю профильную операцию, включая последующие шаги.
`operation_id` добавлен в JSON-отчёт; существующий `backup` сохранён.

Snapshot покрывает текущие отслеживаемые пути, выбранные assets, фактические файлы
curated-полей, предыдущий apply-journal и затрагиваемые им пути, active-profile,
Konsole, include-файлы терминалов и каталог обоев. Учитываются XDG и существующие
symlink-назначения корней. Слишком широкий пользовательский путь, включающий
сами бэкапы/служебные записи, отклоняется до начала применения.

При ошибке записи, журнала или обязательного внешнего шага Rust фиксирует
состояние после ошибки и восстанавливает оригиналы; новые файлы удаляются,
права и ссылки возвращаются. Каталоги удаляются только пустыми. Сверяется
получившееся дерево. Восстанавливаются захваченные GSettings, запрашиваются
перечитывание оформления/KWin/kitty и запуск plasmashell. После внешних вызовов
оригинальные байты проверяются и при необходимости возвращаются повторно.
Ошибка применения и ошибка восстановления сообщаются отдельно; бэкап остаётся.

Ошибки доступных команд применения цветов/курсоров/Plasma/Kvantum/kwriteconfig,
таймаут bat и неудачный запуск plasmashell больше не считаются успешным Apply.
Необязательные уведомления D-Bus, отсутствующие приложения и пользовательские
reload hooks остаются best effort: приложение может быть закрыто, эффект — отсутствовать.

Запуск Plasma проверяется по активной `plasma-plasmashell.service`, а если служба
неактивна — по ответу `org.kde.plasmashell` на D-Bus Peer.Ping.
Работающая вне systemd оболочка не создаёт ложную ошибку восстановления и блокировку.

## Прерывание процесса и восстановление

```bash
kolira operations list
kolira operations show apply-ABC123
kolira operations recover apply-ABC123
```

Состояние `preparing/applying/recovering/recovery_failed` без владельца блокировки
показывается как `interrupted:true`. GUI сообщает о нём один раз при обновлении
списка профилей; `status` содержит `apply_operation_busy` и `apply_recovery_required`.
`apply_operation_busy` отражает реально занятую блокировку. Историческое имя
`apply_recovery_required` сохранено для совместимости: это список операций,
которые можно восстановить, а не запрет следующих изменений. GUI показывает
предупреждение с бэкапом и командой восстановления. После освобождения блокировки
применение другой темы, удаление снимков и другие операции доступны сразу.
Незавершённая подготовка без начала записи отменяется как `cancelled_preparation`.
Прерванный процесс не может выполнить откат сам; восстановление запускается явно.

Обычное восстановление сравнивает текущие файлы с сохранённым состоянием после
операции. Если файлы изменены позднее, оно отказывает **до записи** и перечисляет
конфликты. При SIGKILL в середине Apply состояние после записи может быть неизвестно;
такое расхождение тоже считается конфликтом. После просмотра бэкапа и сохранения
нужных личных правок можно явно запросить замену:

```bash
kolira operations recover apply-ABC123 --force
```

`--force` заменяет файлы в захваченном наборе оригиналами, включая личные изменения
после сбоя. Он не обходит проверку целостности бэкапа. Ошибки восстановления имеют
код выхода 1, запись остаётся `recovery_failed`; её можно повторить после устранения
причины. API GUI/MCP-адаптера: `operation.list`, `operation.recover` ([API](CORE_API.md)).

## Границы

- Это восстановление файлов и проверяемых синхронных шагов, не атомарная транзакция
  файловой системы с D-Bus. Состояние произвольных работающих приложений полностью
  восстановить невозможно. После SIGKILL могут оставаться внешние процессы;
  перед принудительным восстановлением следует дождаться их завершения.
- Внешние программы не соблюдают нашу блокировку. Откат после обычной ошибки
  возвращает захваченный набор к состоянию перед Apply; посторонние записи внутри
  этого набора во время самой операции могут быть заменены. Личные ключи вне
  затронутых файлов и файловые изменения после сохранённого checkpoint защищены.
- Установки зависимостей выполняются собственными исполнителями; новые установленные
  ресурсы/пакеты и их реестр не удаляются откатом оформления. Подготовка конфигов
  проверяется до установок; их собственные ошибки восстановления видны отдельно.
- Inspector сохраняет свою модель частичного Apply и staging для retry; общая
  блокировка не превращает его в профильную транзакцию. То же относится к отдельным
  операциям палитры и обоев.
- Новые пустые родительские каталоги вне захваченных корней могут остаться.
  Записи операций и бэкапы здесь не ограничиваются десятью: UI и политика хранения
  последних 10 смен тем остаются отдельной задачей.
- Проверки выполняются в изолированных HOME/XDG. Настоящие Plasma-хуки и установки
  зависимостей в этой задаче не запускались.

## Подтверждение предварительного просмотра

GUI Apply использует [просмотр изменений](APPLY_PREVIEW.md). Токен проверяется
под общей блокировкой, включая подготовленный источник, до первой записи.
Устаревший план отклоняется без применения; повторное подтверждение явно.

## История последних смен и восстановление завершённой операции

`operations/<id>.json` дополнительно хранит `source` (`cli`, `gui`, `mcp`,
`schedule`), `previous_profile`, полный/частичный `report` (включая изменённые
пути) и `restored_operation` для восстановления. Старые записи читаются с
пустыми дополнительными полями; неизвестная исходная тема не угадывается.
Повторное применение той же темы создаёт отдельную запись.

После завершения остаются 10 последних завершённых записей по времени начала
и **все** записи, требующие восстановления. Старые бэкапы не удаляются при
сокращении истории: лимит журнала не является политикой удаления резервных копий.
Копии видимых записей доступны до их явного удаления пользователем. Отдельной
автоматической очистки бэкапов пока нет.

`kolira operations list` и `core operation.list` возвращают состояние
блокировки, историю, `interrupted`, `backup_status` (`not_created`, `available`,
`unavailable`), `backup_error` и `can_restore`. Доступность проверяется по
манифесту и хэшам сохранённых оригиналов, а не только существованию каталога.
В GUI история доступна через «История смен тем»: подробности, открытие бэкапа,
подтверждаемое восстановление. Успешный apply не показывает всплывающий отчёт;
при ошибке можно открыть историю. Ошибки расписания обнаруживаются при опросе
истории работающим GUI. При закрытом GUI они сохраняются до следующего запуска.

Для завершённой смены:

```sh
kolira operations restore OPERATION_ID --confirm
```

JSON: `core operation.restore` с `id`, `confirmed: true`, опциональным `source`.
Команда заменяет текущее состояние исходным состоянием выбранной операции,
сначала создавая собственную транзакционную копию `backups/pre-restore-*`.
Восстановление получает новый ID и связано с исходным через `restored_operation`;
при сбое оно откатывается к своей страховочной копии. Повреждённый/отсутствующий
оригинал отвергается до живых записей. Незавершённые записи истории не блокируют
этот путь; блокировка исключает только параллельную выполняющуюся операцию.
